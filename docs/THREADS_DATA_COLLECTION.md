# Threads fixture collection and privacy

25 October 2026 (Asia/Kuala_Lumpur). All objects, grants, accounts and text used in Phase 3B are synthetic. No person-level author store, public discovery, external AI processing, publishing, moderation or media download exists.

## Fixed contracts and bounded work

`ThreadsClient` implements the Phase 3A code/long/refresh/debug/own-profile/own-posts/replies/conversation contracts. Requests are typed operations, with fixed `graph.threads.com` paths and `v1.0` on collection/profile reads. Numeric remote identifiers remain exact strings, including oversized JSON integers. No caller supplies a URL. Returned `paging.next` is only a more-pages signal; the client never follows or stores it. Only the bounded `after` cursor is reconstructed into the fixed operation. Reply calls do not invent undocumented `limit`, `since` or `until` parameters.

The future transport contract records verified TLS peer/hostname, HTTPS only, no redirects, 3-second connect and at most 20-second total deadlines, no verbose logging and identity encoding. **No live adapter executes these options in this phase**; streaming header/body/decompression enforcement requires a later adapter review. The current fake/client enforce one-MiB bodies, bounded JSON nesting/structural complexity, field projections, at most 100 returned records and safe errors. Oversize/malformed/schema-drift responses do not publish partial transport data.

The worker retains 25-second/96-MiB defaults. A shared budget permits one provider request per invocation and reserves four seconds before the deadline for persistence/cleanup. A provider unit ends the worker's provider processing, including failure; local maintenance may have run first. There is no retry sleep or persistent worker. Local per-account reservation policy is one in-flight request, 60 requests per fixed hour, a 90-second crash reservation and a conservative 60-second throttle pause plus queue backoff. These numbers are local fixture safeguards, **not Meta quota entitlements or reliable header telemetry**. Preflight deferral moves availability without consuming queue/provider attempts; actual/unknown requests count conservatively.

## Collection and provenance

Create a run for owned posts, top-level replies or a root conversation. The authenticated owner selects a half-open UTC interval of at most 30 days. There are at most ten active runs/account, ten pages/run and 1,000 observed records/run. Root-specific imports require a retained, unblocked, unexpired `owned_post` internal reference. Pasted provider IDs and replies used as roots fail. The owned-list response must carry an owner ID matching the connected account; missing or mismatched evidence blocks publication. The own-profile endpoint is always `/me`, never an arbitrary user history lookup.

Incremental owned-post runs begin one hour before the latest exhausted owned-post window, capped to the new end minus 30 days. If operational history expired, use the bounded 30-day fallback. Repeated/overlapping runs upsert exact scoped media IDs. This is a polling overlap, not a permanent provider change feed or proof of deleted items.

`content_items` unifies roots and replies so direct/conversation overlap cannot create two content objects. Store nullable text/time/handle/permalink and remote root/parent references; an unreturned parent is not fabricated. Known contradictory roots, a root returned as its own reply, direct replies with a contradictory parent and conflicting existing local root context fail. A missing reply root field can rely on the verified root-specific request provenance; it stays null in remote evidence.

Reply media ID is never an author ID. The database enforces `author_user_id IS NULL`; usernames remain mutable observations. No exact distinct-person metric or complete visibility claim exists. Missing text/handles stay null. Unknown-time objects are counted separately and their bodies excluded from the dated sample. Reply windows are filtered locally, and overfetch is disclosed. Permalinks are allowlisted HTTPS display references and are never fetched.

Current text/context hashes increment `source_version` on edits. Preserve first collection, last verification, expiry, endpoint/API/projection version, run/window, grant revision, missingness and accessible-sample provenance. Re-fetch never extends the original source lifetime. Reply expiry is no later than its root expiry. No raw response archive is kept. No future analysis is silently implemented by retaining this evidence.

Run outcomes distinguish pending/running, exhausted accessible pass, partial, blocked, failed and cancelled. A cursor cycle, cap, malformed page or lost authorization cannot become an empty successful collection. `records_retained` counts retained observations in the pass, including overlap; it is not a unique audience or global content count.

## Queue publication and crash recovery

Registered types are `threads.token`, `threads.validate`, `threads.posts`, `threads.replies` and `threads.conversation`. Payload version 1 contains only internal account/run/checkpoint version or an allowlisted lifecycle step; no credential, cursor, body, arbitrary URL or remote root ID is accepted. Jobs have composite account FKs and immutable account privacy/credential/grant snapshots.

The common order is organization/synthetic scope, account, job, then run/checkpoint/content. The one-account pilot lets the queue lock its account before any job, including retention. The claim transaction reserves an ownership-bound account slot for the configured lease (90 seconds by default), closing the gap before preparation without counting a provider attempt. A short fenced pre-call transaction checks grants, run/root versions and suppression, converts that owned slot to a request reservation and opens the encrypted token/cursor; it commits before the fake request. The remaining call deadline is recalculated after preflight so database overhead cannot consume the four-second persistence reserve. Publication rechecks scope/lease/token/generation/privacy/grant/source/checkpoint/reservation, upserts page data, advances the encrypted cursor/hash history, dispatches the deterministic continuation and marks success atomically. The final lease check can roll the whole publication back. Handler-owned lifecycle version changes occur under that same account lock; the final check preserves original lease/organization ownership without rejecting its own approved credential update.

Killed workers recover through Phase 2's finite leases/backoff/attempts. Unknown request outcomes can repeat remotely in a future live implementation. Idempotent local storage never promises exactly-once execution or billing. Terminal/recovered collection failures record an explicit partial outcome.

## Retention, deletion and restore

The Phase 2 synthetic sweep now selects only known demo job types. The Threads extension cleans its actual FK graph: checkpoints before runs; replies before roots; attempts before jobs; credentials/grants/states/request metadata before a minimal disconnected account tombstone. Cleanup is bounded to 100 dependency rows/category, with at most ten expiry intents prepared per sweep and continuation jobs for further work. No foreign keys are disabled and no whole corpus is loaded. Account blocking is a parent read fence, avoiding an unbounded update of all bodies during disconnect.

Finite source retention applies to bodies/handles/provenance, roots and replies. Profile display handles have finite expiry; current shorter policy bounds apply to reads and sweeps. State has ten-minute access expiry; credentials and grants have separate expiries; request/run/job metadata follows bounded operational retention. Expired grants cannot authorize reads. Tokens and display identity are removed on disconnect/revocation; only minimal local scope/epoch/suppression proof remains. Suppression/key lifecycle beyond the last restorable backup requires operator review; it is not an indefinite permission to retain source evidence.

Account, source and Threads-organization deletion write version-2 content-free signed intents to a separate `threads-deletions.jsonl` in the existing independent private ledger directory. Source references are HMACs bound to provider/fixture app/organization/account scope, with no raw media IDs, usernames, text or tokens in the ledger. A source deletion increments the containing account epoch and cancels its in-flight work. A blocked/expired root immediately blocks child reads even before physical purge. Import checks the suppression HMAC before every upsert. Other tenants/accounts are outside the deletion predicates and composite FKs.

For an isolated local/test restore, keep web/cron stopped. Replay **both** independent ledgers from offset zero with `privacy:replay-ledger` and `privacy:replay-threads-ledger`; continue returned offsets until done. Replay is conservative even when primary completion had previously been recorded; it regenerates purge work under the new epoch. Absent source/account targets still leave suppression records. Run bounded cleanup until primary manifests complete and prove negative reads/imports before reopening. Preserve the independent signing key and a separately protected complete ledger position/checksum; HMAC does not detect deletion of whole records.

This implements a synthetic restore-suppression drill, not encrypted cPanel backup recovery. Primary completion says nothing about provider logs, downloaded exports or measured backup erasure. The pre-existing 500-entry installation log/session directory scan still lacks a persisted cursor; no full-installation retention certification is claimed. No analysis/report/private-content exports exist in this phase, so no fictitious derivative purge is claimed.
